# Current OpenBao Integrated Storage (Raft + bbolt) Architecture Audit 🤖

## Executive Summary
This audit provides an exhaustive architectural decomposition of OpenBao's Integrated Storage engine, implemented via HashiCorp Raft (`github.com/hashicorp/raft v1.7.3`) and bbolt (`go.etcd.io/bbolt v1.5.0`). In Cloakit Privacy Vault's deployment topology, OpenBao operates as a Layer 2 Subject Key management and cryptographic processing engine handling a target 95% read / 5% write workload (Subject Key lookups, DEK wrap/unwrap operations beneath Layer 1 KMS/HSM KEKs and above Layer 3 PostgreSQL DEKs).

This analysis examines the exact storage abstractions, database files, bucket layout, lifecycle initialization, FSM execution paths, and differences between local reads and replicated writes.

---

## 1. Physical Storage Architecture & Filesystem Topology

OpenBao Integrated Storage persists data across two distinct bbolt database instances housed within the filesystem directory designated by `BAO_RAFT_PATH` or the `path` configuration parameter (`internal/physical/raft/raft.go:360-366`):

```
${BAO_RAFT_PATH}/
├── node-id                   [Plaintext local node UUID, 0600 mode]
├── vault.db                  [bbolt: Application State Store (FSM data)]
└── raft/
    ├── raft.db               [bbolt: Raft LogStore & StableStore]
    └── snapshots/            [Directory: BoltSnapshotStore tar/gz archives]
        └── <term>-<index>-<timestamp>.tmp / ...
```

### 1.1 `vault.db` (Application State Database)
- **Source File**: `internal/physical/raft/fsm.go:45` (`databaseFilename = "vault.db"`).
- **Owner**: Managed exclusively by `FSM` (`internal/physical/raft/fsm.go:107-140`).
- **Purpose**: Houses the encrypted state of OpenBao (Transit keys, secrets, auth tokens, system configuration).
- **Bucket Hierarchy**:
  1. `data` (`internal/physical/raft/fsm.go:50`): Stores all key-value entries. Keys are hierarchical paths (e.g., `sys/mounts`, `transit/keys/<subject-key-id>`), values are encrypted bytes.
  2. `config` (`internal/physical/raft/fsm.go:51`): Stores internal FSM consensus metadata:
     - `latestIndexKey` (`[]byte("latest-index")`): Protobuf-encoded `IndexValue` (`term`, `index`) representing the last applied Raft log (`fsm.go:53, 238-248`).
     - `latestConfigKey` (`[]byte("latest-config")`): Protobuf-encoded `ConfigurationValue` tracking cluster server configuration (`fsm.go:54, 251-260`).
     - `localNodeConfigKey` (`[]byte("local-node-config")`): Node-specific suffrage state (`fsm.go:55, 329-335`).

### 1.2 `raft.db` (Consensus Log & Stable Store)
- **Source File**: `internal/physical/raft/raft.go:453` (`filepath.Join(path, raftState, "raft.db")`).
- **Owner**: Managed by `raftboltdb.BboltStore` (`github.com/hashicorp/raft-boltdb/v2`).
- **Purpose**: Implements `raft.LogStore` (replicated Raft write-ahead logs) and `raft.StableStore` (persisting current consensus `Term` and `Vote`).
- **Bucket Hierarchy**:
  1. `logs`: Raft log entries indexed by 64-bit big-endian integer keys (`uint64`).
  2. `conf`: Stable consensus metadata (current term, candidate voted for).

## 2. Initialization and Lifecycle Tracing

### 2.1 Backend Initialization (`NewRaftBackend`)
- **Source**: `internal/physical/raft/raft.go:359-586`.
- **Classification**: `SOURCE-CONFIRMED`.
- **Initialization Steps**:
  1. **Path and Node Identification** (`raft.go:360-415`): Reads node ID from `BAO_RAFT_NODE_ID`, config `node_id`, or persists a generated UUID to `${path}/node-id`.
  2. **FSM Instantiation** (`raft.go:418-421`): Calls `NewFSM(path, localID, logger.Named("fsm"))` (`internal/physical/raft/fsm.go:144`). This invokes `openDBFile(filepath.Join(path, "vault.db"))` (`fsm.go:198-269`), opening `vault.db` with options generated by `boltOptions()` (`raft.go:2179`), creating buckets `data` and `config`, and loading `latestIndex` and `latestConfig` into `atomic.Uint64` / `atomic.Pointer`.
  3. **Raft Store Instantiation** (`raft.go:453-465`): Opens `${path}/raft/raft.db` using `raftboltdb.New(raftOptions)`.
  4. **Log Cache Wrapping** (`raft.go:467-471`): Wraps the log store in `raft.NewLogCache(512, store)`. The cache size is hardcoded to 512 entries (`raftLogCacheSize = 512`, `raft.go:80`).
  5. **Snapshot Store Instantiation** (`raft.go:474-478`): Initializes `NewBoltSnapshotStore(path, ...)` (`internal/physical/raft/snapshot.go:83`).
  6. **Concurrency Pools Configuration** (`raft.go:576-577`): Initializes two permit pools:
     - `permitPool = physical.NewPermitPool(128)` (`physical.DefaultParallelOperations`).
     - `txnPermitPool = physical.NewPermitPool(64)` (`physical.DefaultParallelTransactions`).
  7. **Autopilot & Non-Voter Configuration** (`raft.go:550-564`): Determines suffrage mode (`non_voter` or permanent read replica).

### 2.2 Cluster Setup and Leadership Lifecycle
- **Cluster Startup** (`internal/physical/raft/raft.go:951-1210`): Instantiates transport (`raftLayer`, `raft.NewNetworkTransport`), applies Raft configurations via `applyConfigSettings` (`raft.go:821-906`), registers FSM, and launches the Raft node.
- **Log Truncation Worker** (`raft.go:1921-1939`): Once active, starts background log truncation loop (`startLogTruncationWorker`) running on `snapshotInterval` (default 120s) plus jitter.

## 4. Local Reads vs Replicated Writes Analysis

### 4.1 Local Reads (`Get`, `List`, `ListPage`)
- **Source**: `internal/physical/raft/raft.go:1714-1817` and `internal/physical/raft/fsm.go:506-607`.
- **Classification**: `SOURCE-CONFIRMED`.
- **Mechanism**: Local reads are executed **directly against the local `vault.db` FSM** without engaging Raft consensus, Raft log generation, or network RPCs.
- **Consistency Semantics**:
  - On the **Active Leader**: Guarantees read-after-write consistency (monotonic reads) because writes are committed to the local FSM before the write RPC returns (`raft.go:1820-1919`).
  - On **Followers / Non-Voter Replicas**: Reads reflect the locally applied FSM state. If follower replication lags behind the leader, reads are subject to stale reads (bounded eventual consistency). OpenBao does not implement ReadIndex or LeaseRead RPCs for storage-level reads; reads query the local mmap directly.

### 4.2 Replicated Writes (`Put`, `Delete`)
- **Source**: `internal/physical/raft/raft.go:1746-1774`, `1822-1919`, and `internal/physical/raft/fsm.go:731-929`.
- **Classification**: `SOURCE-CONFIRMED`.
- **Mechanism**: Replicated writes **must** be submitted to the active Raft leader, serialized as Protobuf `LogData`, committed to the leader's `raft.db`, replicated over TLS transport to a quorum of voting peers, acknowledged, applied to the leader's and followers' `vault.db` via `FSM.ApplyBatch`, and fsynced.

## 5. Node Roles: Leader, Follower, Non-Voter

| Architectural Property | Active Leader | Follower (Voter) | Read Replica (Non-Voter) |
| :--- | :--- | :--- | :--- |
| **Consensus Voting** | Holds election vote, coordinates terms | Votes in elections, participates in quorum | Zero vote weight (`NodeNonVoter`, `raft.go:62`) |
| **Write Execution** | Accepts writes, writes to `raft.db`, coordinates replication | Rejects direct writes; redirects to leader | Rejects direct writes; redirects to leader |
| **FSM Application** | Calls `ApplyBatch` upon quorum consensus | Calls `ApplyBatch` upon leader AppendEntries | Calls `ApplyBatch` upon leader AppendEntries |
| **Read Execution** | Serves reads from local `vault.db` (Strong) | Serves reads locally if standby reads enabled (Stale) | Serves reads locally without quorum overhead |
| **Quorum Impact** | Requires $(N/2)+1$ acknowledgments | Included in $N$ calculation | $0$ impact on write quorum or election quorum |

## 6. Architectural Suitability for Cloakit Privacy Vault

| Cloakit Requirement | Integrated Storage Reality | Evaluation / Architectural Risk |
| :--- | :--- | :--- |
| **95% Reads / 5% Writes** | Direct mmap reads bypass Raft consensus entirely. | **Highly Favorable**: Read path scales with local memory and CPU; does not burden consensus network. |
| **High Subject Key Cardinality** | bbolt stores keys in a single flat bucket `data`. | **Moderate Risk**: High cardinality (>1M keys) increases B-tree depth (4-5 levels) and page boundary splits. |
| **Frequent DEK Wrap/Unwrap** | Transit engine key lookup queries cache first (`TwoQueueCache`/`sync.Map`), falling back to `b.Get()`. | **Favorable if Cached; Bottleneck if Missed**: Cache hit requires 0 storage I/O. Cold cache incurs `permitPool` lock + bbolt mmap page read. |
| **Multi-Node Concurrency** | bbolt enforces a strict single-writer mutex (`tx.lock.Lock()`). | **Severe Write Bottleneck**: Concurrent writes block on bbolt write transaction lock, serializing FSM applies. |
| **Durability & Recovery** | Two fsyncs per write: (1) `raft.db` log commit, (2) `vault.db` FSM apply commit. | **High Durability / Low Write IOPS**: Every write incurs dual synchronous disk fsyncs. |
